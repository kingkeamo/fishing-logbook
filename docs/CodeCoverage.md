# Code coverage

Every pull request targeting `main` is checked for coverage regressions. The check fails if overall
**line** or **branch** coverage is lower than on the target commit. There is no fixed minimum
percentage; the goal is only that coverage never silently goes down.

## What is measured

- `coverlet.collector` (already referenced by every test project) collects Cobertura reports using
  [`coverage.runsettings`](../coverage.runsettings).
- Reports from all test projects are merged into one aggregate. Each source file is attributed to
  its production project from its `src/<Project>/` path (file names in coverlet reports are relative
  to a report-specific root, so the report's `<source>` is combined with the file name first).
  Paths from Windows and Linux runs therefore produce identical keys.
- Merging is per line: a line counts as covered if any report hit it, and its branch coverage is
  the best covered/total seen in any report. Coverage of production code by a *different* test
  project (for example the API tests exercising Application code) therefore counts. Because branch
  coverage per line is taken as the maximum rather than a true union, the figure is a slightly
  conservative lower bound, identically for baseline and PR.
- Projects measured: everything under `src/` that a test project loads â€” Api, Application, Client,
  Db.Migrations, DependencyInjection, Domain, Infrastructure, Mobile (the `net10.0` presentation
  code only), Shared and Web.

### Exclusions

Only generated code is excluded, and the list is deliberately short:

| Exclusion | Why |
|---|---|
| Files under `obj/` or `bin/`, `*.g.cs`, `*.designer.cs` | Generated by the compiler, Razor and source generators; not authored. |
| Test assemblies (`*.Tests`, `FishingLogBook.Tests.Common`) | Not production code. |
| Code with `GeneratedCode`, `CompilerGenerated` or `ExcludeFromCodeCoverage` attributes | Generated or explicitly declared non-testable. |

The list lives in `coverage.runsettings` and `.github/coverage/coverage.config.json`. Nothing else
(including `Program.cs`, migrations and composition roots) is excluded; it all counts. The gate
fails if either file differs from the baseline's, or if any exclusion is added, so exclusions
cannot be used to pass a PR. Changing the configuration deliberately requires a maintainer to
approve the PR and let the next `main` run publish a new baseline.

### Mobile

`FishingLogBook.Mobile.Tests` (`net10.0`) runs on Windows in its own `mobile-coverage` job in
`build-test.yml`. It repeats the invocation of the `mobile-build-test.yml` android job (tests
before any MAUI build, with hang diagnostics) with coverage added, so that existing workflow is
unchanged.

*Why the Mobile tests run twice.* The alternative is to collect coverage in the `mobile-build-test.yml`
android job and have the gate in `build-test.yml` fetch that artifact from the sibling workflow run
for the same commit. That needs the gate to poll another workflow (which can be re-run, cancelled or
slow independently), so a missing or stale Mobile report becomes a race instead of a clear failure,
and it widens the gate's dependency on a workflow whose tests deliberately run before the MAUI
builds because of a known `testhost` hang. The duplicate costs one extra Windows job; the
single-workflow design keeps the gate deterministic. Duplication can be removed by restructuring
the workflows around a shared prerequisite mobile test job, with both the coverage gate and
platform builds depending on it. That requires coordinated changes to both workflows and their
required checks. Revisit if Windows minutes become a concern: a Linux runner may work once the
MAUI Android workload restore is verified there. Platform-specific `net10.0-android` / `net10.0-ios` code is not part of the `net10.0`
test build and is therefore not measured; it needs emulator or device verification instead.

## How the gate works (`build-test.yml`)

| Job | Purpose |
|---|---|
| `build-test` | Existing .NET build and test, now with coverage collection (one test run, not two). Uploads `coverage-raw-dotnet`. |
| `mobile-coverage` | Mobile presentation tests with coverage. Uploads `coverage-raw-mobile`. |
| `coverage-gate` | Merges the reports, uploads `coverage-summary`, and for PRs to `main` compares with the baseline. This is the check to mark as required. |

On every push to `main` the same workflow publishes a `coverage-summary` artifact (retained 90
days). For a PR the baseline is the artifact of the successful `build-test` run on `main` whose
head commit is exactly the PR's target (`pull_request.base.sha`) â€” not "the latest run". The gate
fails with an explanatory message when that run is missing, failed, still running after 30
minutes, has an expired artifact, or has an incompatible schema. Re-run `build-test` on `main`
(Actions â†’ build-test â†’ Run workflow) or update the PR branch to fix a missing baseline.

The gate never treats absent data as success. It also fails when:

- any test job failed or was cancelled (the gate uses `if: always()` so it cannot be skipped);
- fewer than the expected seven Cobertura reports are present, a report is unparseable, or totals are zero;
- a production project that still exists under `src/` has no coverage data;
- the coverage configuration or exclusions changed (see above).

Comparisons use exact `covered / total` ratios with a `1e-9` floating-point tolerance, not rounded
percentages. Added files are counted in the totals (new untested code lowers coverage; new tested
code does not), and removed files simply drop out.

### Results

The job summary shows the Main / PR table for line and branch coverage, a per-project table
that flags any project whose coverage decreased (a project decrease alone does not fail the
gate; the overall metrics decide), and informational changed-line coverage computed from the
PR's diff. Downloadable artifacts: `coverage-summary` (`coverage-summary.json`, merged
`coverage.cobertura.xml`, markdown), `coverage-comparison`, `coverage-raw-*`.

### Bootstrapping

The PR that introduces the gate has no baseline: its target commit does not contain
`.github/coverage/coverage.config.json`. In exactly that case the gate prints a warning and passes.
Once merged, the push to `main` publishes the first baseline and every later PR is compared.
Add `Coverage regression gate` to the branch protection required checks after that run.

## Running locally

```bash
dotnet test tests/FishingLogBook.Shared.Tests --collect:"XPlat Code Coverage" \
  --settings coverage.runsettings --results-directory coverage/raw/dotnet
# repeat for the other test projects; Mobile needs: -f net10.0 and, on a machine whose Android SDK
# is not in the default location, -p:AndroidSdkDirectory=<sdk path>, with --results-directory coverage/raw/mobile
node .github/scripts/coverage/coverage.mjs merge --input coverage/raw --output coverage/current --sha local
```

Open `coverage/current/coverage-summary.md`, or `coverage.cobertura.xml` with any Cobertura viewer.
To compare two runs, produce `coverage-summary.json` for each and run:

```bash
node .github/scripts/coverage/coverage.mjs compare --baseline main/coverage-summary.json --current coverage/current/coverage-summary.json
```

Run all 38 coverage tests with:

```bash
node --test .github/scripts/coverage/coverage.test.mjs .github/scripts/coverage/resolve-baseline.test.mjs
```

Both suites also run in the `deployment-config-test` CI job. They exercise the real CLI with
temporary reports and repositories, and the baseline resolver against a local HTTP API fixture.

## Limitations

- Branch coverage is a per-line maximum across reports (a conservative lower bound), not a union of individual branches.
- The workflow and scripts live in the repository, so a PR could edit them. Protect `.github/`,
  `coverage.runsettings` and the coverage config with CODEOWNERS or a ruleset if that matters.
- Coverage of `net10.0-android` / `net10.0-ios` code is not measured (see Mobile).
- The baseline is per target commit; if `main` advances after a PR's last run, the PR is still compared with the commit it was tested against.
